# Промпт для Claude Code — Vibentry v1.1 (дизайн + 3 задачи)

Скопируйте блок ниже первым сообщением в Claude Code, открытом в корне проекта. Перед этим распакуйте архив `vibentry-design-v1.1.zip` поверх проекта (файлы встанут по своим путям).

---

Ты работаешь над проектом Vibentry (Telegram Mini App + бот, платный курс по вайбкодингу). Сначала прочитай `CLAUDE.md`, `handoff/CHANGES_v1.0_design.md`, `handoff/CHANGES_v0.5.md` и `README.md`. Правила из `CLAUDE.md` обязательны: проверка доступа на сервере по initData, платёж засчитывается только после подтверждения у провайдера, секреты только в `.env`, CSP без inline-стилей и скриптов, весь текст для читателя на «вы», шрифт не меньше 11 px, область нажатия не меньше 44 px, никаких выдуманных цифр, кейсов и отзывов. Тесты (`npm test`) должны оставаться зелёными, на каждую новую серверную функцию добавляй тест.

## Дизайн (уже сделан, не переделывай)
`public/design.css` подключён после `style.css`. Новые экраны и блоки строй на его токенах: `--bg --surface --surface-2 --line --line-2 --ink --ink-2 --ink-3 --accent --gold`, оттенки модулей `--h1..--h4` (классы `hue-1..hue-4`), радиусы `--r-lg --r-md --r-sm`. Принципы: плоские поверхности и линии 1px, без теней, градиентов и свечений (исключения — hero и «промпт дня» уже оформлены); лайм `--accent` только на главном действии и прогрессе; списки — строками с разделителями, не карточками. Готовые элементы для повторного использования: `.stat-tile`, `.path-card`, `.cat-chip`, `.copy-quick`, `.segments`, `.chips`, `.admin-card`. Если нужен новый стиль — дописывай в конец `design.css`, не в `style.css`. Светлую тему не делай.

## Задача 1. Живая проверка оплаты, ссылок и бота
Цель: всё, что я не мог проверить без реального сервера, должно быть проверено и сведено в понятный отчёт.
1. Запусти `npm run check-links`. Битые ссылки исправь в источнике (`data/*.json`, `scripts/import-package.mjs`), спорные перечисли отчётом. Ссылку Ahlis Shop в курсе оставь.
2. Добавь в админку экран «Проверка системы» (вкладка в `public/js/admin.js`, маршрут `GET /api/admin/health`, только для админов). Он показывает построчно, зелёным или красным, с причиной: бот отвечает (`getMe`) и username совпадает с конфигом; бот состоит в каждом обязательном канале и может проверять участников (`getChatMember` по тестовому пользователю-админу); `PUBLIC_URL` доступен по https; для каждого провайдера — ключи заданы, ping API провайдера проходит; вебхуки провайдеров зарегистрированы; запись в базу работает; время последней успешной оплаты. Секреты и их фрагменты в ответ не попадают.
3. Подготовь пошаговый файл `handoff/LIVE_TEST_RU.md` для ручной проверки: тестовый платёж Stars (оплата, `successful_payment`, возврат через `refundStarPayment`, пропажа доступа); Platega и CryptoBot (используй testnet CryptoBot, `@CryptoTestnetBot`), повторная доставка вебхука не даёт двойного доступа, неверная сумма и валюта отклоняются; xRocket — сверь реальные имена полей по их документации и убери флаг `needsSandboxCheck` только после успешного теста; промокод; гейт каналов. Каждый пункт: что сделать, что должно произойти, что проверить в админке.
4. Чего не умеешь проверить сам — не отмечай как проверенное, выноси в отчёт «нужно сделать владельцу».

## Задача 2. Избранное и «недавно открытое»
1. Сервер: таблица `favorites(user_id, kind, item_id, created_at)`, kind ∈ `prompt|lesson|article`, уникальный ключ на три первых поля. Маршруты `GET /api/favorites`, `PUT /api/favorites/:kind/:id`, `DELETE /api/favorites/:kind/:id`. Проверяй существование элемента, лимит 200 закладок на пользователя, rate limit как у остальных пользовательских маршрутов. В ответе только id, kind и заголовок, текст уроков и статей не отдаётся (правило 3 из `CLAUDE.md`). Закладки на платные элементы Free-пользователь поставить может, открыть без доступа — нет.
2. Клиент: кнопка-звёздочка (44 px, `aria-pressed`, состояние меняется сразу, при ошибке откатывается с понятным тостом) на строке промпта рядом с `.copy-quick`, в шапке урока и в шапке статьи базы. В «Материалах» добавь четвёртую вкладку «Избранное» (`.segments` перестроить на 4 колонки без потери читаемости на 360 px) со списками по типам и честным пустым состоянием: что это и как добавить.
3. «Недавно открытое»: последние 6 элементов (урок, промпт, статья) хранить в `localStorage` с try/catch, показывать строкой-лентой на главной между «Путём курса» и «Промптом дня», если список не пуст. Без сервера.
4. Тесты: добавление, повтор, удаление, лимит, чужой id, неизвестный kind, неавторизованный запрос.

## Задача 3. Воронка в админке
1. Сервер: таблица `events(id, user_id, type, meta, at)` с индексом по `(type, at)` и `(user_id, type)`. Допустимые типы (белый список): `app_open`, `lesson_open` (meta: id урока), `lesson_done` (id), `paywall_view`, `checkout_start` (meta: метод), `paid` (пишется только сервером при подтверждённой оплате, клиент его отправить не может), `promo_applied`. `app_open` и `paywall_view` — не чаще раза в сутки на пользователя. Клиент шлёт `POST /api/event` с типом и meta; валидация, rate limit, ответ 204. В событиях только числовой id пользователя, никаких имён и текстов.
2. Админка: вкладка «Воронка» (`admin.js`). Период 7 / 30 дней / всё. Блоки: (а) шаги воронки «Открыли приложение → Открыли урок 1 → Прошли урок 1 → Увидели оплату → Начали оплату → Оплатили» с числом уникальных пользователей и конверсией от предыдущего шага (строки с горизонтальными барами, цвет `--accent` только на последнем шаге); (б) по каждому из 24 уроков: открыли и прошли, чтобы видеть, где отваливаются; (в) оплаты по методам и использование промокодов. Нули печатай как нули, отсутствие данных — как «Пока нет данных за период», без придуманных цифр.
3. Не ломай приватность: экспорт событий и ручной просмотр по пользователю не нужны; в журнал аудита ничего писать не надо.
4. Тесты: запись и дедупликация событий, запрет клиенту писать `paid`, расчёт конверсии на фикстуре, пустой период.

## Порядок и отчёт
Работай в порядке 1 → 2 → 3, после каждой задачи запускай `npm test` и `python3 scripts/browser-smoke.py`, обнови `scripts/browser-smoke.py` под новые экраны. Скриншоты новых экранов (390 и 1280 px) сохраняй в `handoff/screenshots/` с префиксом `v11-`. В конце обнови `CLAUDE.md` (карта файлов), допиши `handoff/CHANGES_v1.1.md` и дай короткий отчёт: что сделано, что проверено реально, что требует действий владельца.
